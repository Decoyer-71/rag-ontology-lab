# 단계 완료 판정

`../../CLAUDE.md` §3 검증 루프 3번 · §7-6. **테스트 통과는 통과가 아니다.**

## ⚠⚠ 왜 이 절차가 있는가

`pytest` 가 초록색이 됐다는 것은 **명세를 만족했다**는 뜻이지 **이해했다**는 뜻이 아니다.
빌려온 코드도, 우연히 맞은 코드도 테스트를 통과한다.

이 저장소의 목적은 이해이고, 기업 지원 포트폴리오로 나간다(§13). **면접에서 무너지는 지점이 정확히 여기다.**
그래서 단계는 **「왜」에 답해야** 닫힌다.

---

## 절차

### 1. 테스트 전체를 돌린다 — 그 단계만이 아니라

```bash
.venv/Scripts/python.exe -m pytest tests/ -q
```

⚠ **앞 단계가 깨지지 않았는지 본다.** 회귀는 조용히 온다.

### 2. 측정 결과가 실재하는지 확인한다 (Stage 3 이후)

- `outputs/metrics/stageNN.json` 이 실제로 있는가
- **기준선 수치가 같이 들어 있는가**(§5-D'). 없으면 아직 안 끝났다
- ⚠⚠ **수치가 이상하게 좋으면 오염을 먼저 의심한다**(§5-E'). Recall@5 ≥ 0.95 는 축하가 아니라 경보다

### 3. ⚠⚠ 「왜」 질문 — 2~3개

`concept-explainer` 가 그 단계에 낸 체크포인트 질문을 쓴다. 없으면 아래 기준으로 만든다.

**질문의 조건:**

| 조건 | 나쁜 예 | 좋은 예 |
|---|---|---|
| 예/아니오로 못 답한다 | "BM25 를 구현하셨나요?" | "IDF 항을 빼면 어떤 질의에서 검색이 망가집니까? 왜죠?" |
| 코드가 아니라 **원리**를 묻는다 | "몇 번째 줄에서 정규화했나요?" | "코사인 유사도가 내적과 다른 결과를 내는 경우는 언제입니까?" |
| **깨지는 조건**을 하나는 묻는다 | — | "이 방법이 원리적으로 못 푸는 질문을 하나 들어 보십시오" |
| **직접 만든 것**을 묻는다 | "일반적으로 청킹은..." | "왜 이 코퍼스에서는 조 단위로 자르는 게 나았습니까? 측정값은 얼마였습니까?" |

⚠ **한 번에 하나씩 묻는다**(§12-3). 세 개를 한꺼번에 던지면 답이 얕아진다.

### 4. 판정

| 답 | 판정 | 다음 |
|---|---|---|
| 원리를 자기 말로 설명한다 | **통과** | §5 로 |
| 코드는 설명하는데 왜인지는 못 말한다 | **부분** | 그 지점만 §7-2 로 되돌아간다. 단계 전체를 다시 하지 않는다 |
| 개념 자체가 안 잡혀 있다 | **미통과** | `concept-explainer` 로 **설명을 다시 설계**한다. 같은 설명을 반복하지 마라 |

⚠⚠ **관대하게 판정하지 마라.** 여기서 넘겨준 구멍은 뒤 단계에서 더 비싸게 돌아온다 —
Stage 2 의 벡터 개념이 안 잡히면 Stage 3·4·9 가 전부 흔들린다.

⚠ **학습자를 평가하지 않는다**(§12-6). *"아직 이해를 못 하셨습니다"* 가 아니라
*"IDF 부분을 한 번 더 보시죠. 그 항이 없으면 어떤 질의가 망가지는지가 핵심입니다"*.

### 5. 진도 갱신

`.claude/state/progress.json`:

```json
{
  "current_stage": <다음 번호>,
  "current_title": "Stage N — ...",
  "completed_stages": [..., <방금 번호>],
  "last_updated": "YYYY-MM-DD"
}
```

⚠⚠ **`completed_stages` 에 번호가 들어가야 `guard_spoiler` 가 그 단계의 `solutions/` 를 열어 준다.**
참조 구현 대조는 **이 시점에** 한다(§3 검증 루프 5번). 그 전이 아니다.

### 6. 기록 — §13-3 의 재료를 만든다

`docs/PROGRESS.md` 에 적는다. **성공만 적지 마라.**

```markdown
## Stage N — <제목>  (YYYY-MM-DD 완료)

- 능력 목표: (한 문장)
- 측정: (기준선 → 결과. ⚠ 분모 포함)
- ⚠ 막혔던 곳: (무엇이 왜 안 됐는지. 없었으면 "없음")
- 폐기한 접근: (시도했다 버린 것과 그 이유. 없으면 "없음")
- 참조 구현 대조 결과: (내 구현과 무엇이 달랐는지)
```

⚠⚠ **「막혔던 곳」과 「폐기한 접근」을 비우지 마라.** README 「배운 것」이 이 두 줄에서 나온다.
*"청킹을 글자수 512로 했더니 요금표가 잘려 숫자 답변이 전부 틀렸다. 조 단위로 바꾸니 Recall@5 가 0.48 → 0.71"* —
**이런 한 줄이 이력서 한 장보다 강하다**(§13-3).

### 7. ⭐ 복습 카드 등록 (§14)

⚠⚠ **여기서 안 만들면 이 단계는 영영 복습되지 않는다.** 카드를 만들 수 있는 곳은 여기뿐이다 —
지금만 「어떤 「왜」 질문을 던졌는가」와 「사용자가 어느 함수를 직접 짰는가」를 둘 다 알고 있다.

**개념 카드** — 절차 3에서 던진 「왜」 질문을 그대로 등록한다.

```bash
.venv/Scripts/python.exe src/labkit/review.py add --stage N --kind concept \
  --target "<개념 이름>" --question "<던졌던 질문 그대로>"
```

**코드 카드** — 사용자가 이 단계에서 직접 구현한 **공개 함수마다** 한 장.

```bash
.venv/Scripts/python.exe src/labkit/review.py add --stage N --kind code \
  --target "src/raglab/<파일>.py::<함수>" \
  --test "tests/test_stageNN_<이름>.py" \
  --question "<이 함수가 무엇을 왜 그렇게 하는지 떠올린 뒤 다시 구현해 보십시오>"
```

⚠ `--test` 를 비우지 마라. **채점을 사람 감으로 하지 않기 위해** 있는 값이다.

⚠ 헬퍼·사소한 함수까지 카드로 만들지 마라. **그 단계의 능력 목표를 담은 함수**만이다.
단계당 코드 카드 2~4장, 개념 카드 2~3장이면 충분하다 — 그 이상은 §9 의 「사용자 시간」을 태운다.

확인:

```bash
.venv/Scripts/python.exe src/labkit/review.py status
```

### 8. 커밋

```bash
git add -A
git commit -m "Stage N: <능력 목표 한 줄>"
```

⚠ 단계별로 쪼갠다. 한 방 커밋은 §13-4 미달이다.

## ⚠ 이 절차를 건너뛰고 싶어질 때

- *"테스트 다 통과했으니 넘어가죠"* → **그게 이 절차가 막으려는 것이다**
- *"시간이 없으니 나중에 확인하죠"* → 나중은 오지 않는다. 그리고 뒤 단계가 이 구멍 위에 쌓인다
- 사용자가 빨리 진행하고 싶어하면 **질문 개수를 2개로 줄이되, 없애지는 마라**
